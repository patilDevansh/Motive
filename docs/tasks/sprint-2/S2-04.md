# Validate and persist shopper event CSV imports

## Description
Accept store-owner event data for later analytics and recommendations, using the catalog storage from S2-03. This slice handles durable, idempotent imports. Statistics, recommendation ranking, UI, and authentication are separate tasks.

## Specs
- `src/event_store.py`: `EventStore(path).import_events(store_id,csv_text)` returns `{inserted,skipped}`; `list_events(store_id)` returns events ordered by timestamp UTC then event_id. Reuse S2-03's SQLite database and product table.
- CSV header exactly `event_id,shopper_id,product_id,event,timestamp` in any order. All values are required. Event is `view`, `cart`, or `purchase`. Timestamp must be ISO 8601 with an explicit timezone offset or `Z`; normalize to UTC with `Z`.
- Each event_id belongs to one store and identifies an immutable row. Reimport of an identical normalized row skips it. Reuse of an ID with different data, including two conflicting rows within one file, rejects the entire file. Unknown product IDs in that store reject the entire file. Duplicate identical rows within a file count as one insertion plus one skip.
- `ImportValidationError.errors` contains `{line,field,message}`. All validation precedes writes; an invalid file leaves the database unchanged. Data remains after reopening the store. An empty CSV body is rejected; header-only input returns zero counts.
- `api/store.py` POST `/stores/{store_id}/events/import` accepts text/csv and returns counts; GET `/stores/{store_id}/events` returns the store's events. Validation errors return HTTP 400 `{errors:[...]}`. This is a local-only service until authenticated.

## Requirements
Depend on S2-03's catalog table and validation error format. Use parameterized SQLite queries and stdlib timestamp parsing. Do not change Retailrocket recommendation behavior. All tests use temporary databases and create a catalog before events.

## Acceptance criteria
1. Unknown products and invalid events are rejected with line/field errors and no partial writes.
2. Identical reimports, including equivalent timezone offsets, do not inflate stored counts.
3. Conflicting event IDs reject the whole file and preserve prior rows.
4. Timestamps normalize to UTC; rows survive reopening the database.
5. Store data remains separate and the HTTP service reports counts, errors, and retrieved events as specified.

## Tests
`tests/test_S2_04_events.py` names start `test_S2_04_`. Fixtures create two stores and catalog products. Tests assert unknown/invalid rollback (1), identical and equivalent-offset skips (2), conflicting IDs and file rollback (3), UTC persistence (4), and store isolation plus HTTP contract (5).
