# Filter per-product event counts by a date range

## Description
Serves the Product-numbers story. Builds on S2-07 (per-product view, cart and purchase counts). Store owners can see counts for a time window, like last week, instead of all time. This task adds two optional query parameters, `start` and `end`, to `GET /stores/{store_id}/products/stats`. Only events inside the window are counted.

Out of scope: the date controls on the dashboard (S2-10), preset ranges such as "last 7 days", grouping counts by day, and changing how S2-04 stores timestamps.

## Specs
- `get_product_stats(db_path, store_id, limit=50, offset=0, start=None, end=None)` in `src/product_event_stats.py` takes two new optional arguments. Each is an ISO 8601 string with a time zone, or `None`.
- New function `parse_time(text, field)` in `src/product_event_stats.py`. It turns an ISO 8601 string into a UTC `datetime`, returns `None` for `None`, and raises `ImportValidationError` for bad input.
- `GET /stores/{store_id}/products/stats` in `api/store.py` takes optional `start` and `end` query parameters, for example `?start=2026-10-01T00:00:00Z&end=2026-10-08T00:00:00Z`.
- The window is start-inclusive and end-exclusive. An event is counted when `start <= event timestamp < end`.
- Times with different offsets that name the same instant give the same result. `2026-10-01T00:00:00Z` and `2026-09-30T17:00:00-07:00` are the same instant.
- If `start` is omitted, there is no lower limit. If `end` is omitted, there is no upper limit. If both are omitted, the result is the same as S2-07.
- The response shape does not change. Every catalog product is still listed, and products with no events in the window have 0 counts.
- Errors return HTTP 400 in the same format as S2-03 and S2-04: `{"errors": [{"line": 0, "field": "<start or end>", "message": "..."}]}`.
  - Not a valid ISO 8601 timestamp (for example `yesterday`): field `start` or `end`, message `Expected ISO 8601 timestamp`.
  - No time zone (for example `2026-10-01T00:00:00`): field `start` or `end`, message `Expected ISO 8601 with timezone`.
  - `start` equal to or after `end`: field `start`, message `start must be before end`.

## Requirements
- Keep S2-07's behavior when no dates are given. The S2-07 tests must pass without changes.
- S2-04 stores `events.timestamp` as UTC ISO text such as `2026-10-01T00:00:00Z` or `2026-10-01T00:00:00.001000Z`. Comparing these as plain text puts `.001000Z` before `Z`, so compare with SQLite's `julianday()` instead.
- Put the date condition in the join, not in `WHERE`, so products with no events in the window are still listed.
- Use parameterized queries and Python's built-in `datetime`. No new libraries.
- Use S2-03's `ImportValidationError` and `error()` for the error format. Do not change S2-03 or S2-04 code.

## Acceptance criteria
1. An event exactly at `start` is counted.
2. An event exactly at `end` is not counted, and an event 1 millisecond before `end` is counted.
3. The same window written with `Z` and with `-07:00` returns identical results.
4. With only `start`, only `end`, or neither, events are limited only by the bounds given. With neither, the counts match S2-07.
5. A window with no events returns every catalog product with 0 for all three counts.
6. `start` >= `end` returns HTTP 400 with field `start` and message `start must be before end`.
7. An unparseable timestamp, or a timestamp without a time zone, returns HTTP 400 with the field and message from Specs.

## Tests
File: `tests/test_S2_08_date_filter.py`
Setup for all: a temporary SQLite file filled with `EventStore` from S2-04. Store `store-a` has products `p1` (Blue Mug) and `p2` (Red Lamp). `p1` has views at 2026-09-30T23:59:59.999Z, 2026-10-01T00:00:00Z (the start), 2026-10-05T12:00:00Z and 2026-10-07T23:59:59.999Z, plus a view at 2026-10-08T00:00:00Z (the end) and a purchase at 2026-10-06T00:00:00Z. `p2` has one view at 2026-11-01T00:00:00Z. The main window is 2026-10-01T00:00:00Z to 2026-10-08T00:00:00Z. API tests use `TestClient(create_app(<tmp database path>))`.

- `test_S2_08_event_at_start_is_counted`: asks for the window and asserts `p1` has 3 views (start, 10-05 and 1 ms before end) and 1 purchase. The view 1 ms before the start is not counted. Covers 1.
- `test_S2_08_event_at_end_is_not_counted`: asks for the window and asserts the 10-08 view is not counted (3 views). Asks again with `end` 1 ms later and asserts it is counted (4 views). Covers 2.
- `test_S2_08_equivalent_offsets_match`: calls the API with `Z` times and with `-07:00` times for the same instants, and asserts both bodies are equal and `p1` has 3 views. Covers 3.
- `test_S2_08_omitted_bounds`: asserts `p1` has 5 views with only `start=2026-09-30T00:00:00Z`, 2 views with only `end=2026-10-05T12:00:00Z`, and 5 views with neither, which equals the S2-07 result. Covers 4.
- `test_S2_08_empty_window_returns_zeros`: asks for 2026-12-01 to 2026-12-02 and asserts both products are listed with 0, 0, 0. Covers 5.
- `test_S2_08_rejects_start_not_before_end`: calls the API with `start == end` and with `start` after `end`, and asserts 400 and the exact error body. Covers 6.
- `test_S2_08_rejects_bad_timestamps`: calls the API with `start=yesterday`, `end=2026-13-01T00:00:00Z` and `start=2026-10-01T00:00:00`, and asserts 400 and the exact error body each time. Covers 7.
