# Require a store API key on store endpoints when authentication is enabled

## Description
Serves the Store-owner-access story (only a store's owner can import or read that store's data). S2-03 and S2-04 left the store service local-only because a store identifier in the URL isolates data but is not a credential: anyone who can reach the service can read or overwrite any store. This task adds per-store API keys and an opt-in mode in which every `/stores/{store_id}/...` request must present that store's key.

Out of scope: owner accounts, passwords, sign-up or login screens, sending the key from the React app, key expiry, more than one active key per store, rate limiting, HTTPS and deployment, and the Retailrocket recommender API in `api/main.py`. Authentication stays off by default so the Sprint 3 upload and dashboard screens keep working until they send a key.

## Specs
- New module `src/store_auth.py`:
  - `StoreKeys(path)` opens the same SQLite file as `CatalogStore` and creates the table `store_keys(store_id TEXT PRIMARY KEY, key_hash TEXT NOT NULL, created_at TEXT NOT NULL)` if it is missing.
  - `StoreKeys.create_key(store_id)` returns a new random key string that starts with `mk_` and is at least 40 characters long. Only the key's SHA-256 hex digest is stored. Creating a key for a store that already has one replaces it, so the old key stops working. A blank store ID raises `ImportValidationError`, as in S2-03.
  - `StoreKeys.verify(store_id, key)` returns `True` only when `key` is the current key of exactly that store, otherwise `False` (wrong key, another store's key, a store with no key, an empty or `None` key).
  - `require_store_keys(app, db_path)` adds the check below to a FastAPI app from `create_app` and returns the app.
- New command `python -m scripts.create_store_key STORE_ID [--db PATH]`. It prints the new key on one line and exits 0. `--db` defaults to `MOTIVE_STORE_DB`, then `motive-store.sqlite3`. This is the only time the key is shown.
- When the check is enabled, every request whose path is `/stores/{store_id}` or starts with `/stores/{store_id}/` is checked before the endpoint runs:
  - No `Authorization` header, or one that is not `Bearer <key>` with a non-empty key: HTTP 401, header `WWW-Authenticate: Bearer`, body `{"errors": [{"line": 0, "field": "authorization", "message": "Missing store API key"}]}`.
  - A key that `verify` rejects for the store in the URL: HTTP 403, body `{"errors": [{"line": 0, "field": "authorization", "message": "Invalid store API key"}]}`.
  - A valid key: the request continues and behaves exactly as without the check.
  - `Bearer` is matched case-insensitively. The store ID from the URL is percent-decoded and trimmed before the lookup, the same way the endpoints treat it.
- A rejected request never reaches the endpoint: a rejected import stores nothing, and its CSV is not validated (the response is 401 or 403, not 400).
- Paths outside `/stores/` (for example `/docs` and `/openapi.json`) are not checked.
- `api/store.py`: the module-level `app` enables the check when the environment variable `MOTIVE_STORE_AUTH` is `required` (case-insensitive). With the variable unset or any other value, behavior is unchanged from Sprint 2 and no key is needed.

## Requirements
- Use only the standard library (`secrets`, `hashlib`, `hmac`, `sqlite3`) and the existing FastAPI/Starlette dependencies. No new libraries.
- Never store, log or return a key after `create_key` returns it. Compare digests with `hmac.compare_digest`.
- Use parameterized SQLite queries. Do not change the `products` or `events` tables or the code in `src/catalog_store.py` and `src/event_store.py`.
- `create_app(db_path)` keeps working without authentication, and the S2-03, S2-04, S2-07 and S2-08 tests pass without changes.
- Tests use temporary databases and FastAPI's `TestClient`.
- Document key creation and the `MOTIVE_STORE_AUTH` setting in `docs/STORE_IMPORTS.md`.

## Acceptance criteria
1. `create_key` returns a key starting with `mk_` of at least 40 characters, two calls return different keys, and the database does not contain the key text.
2. `verify` returns `True` for a store's current key, including after the database is reopened, and `False` for a wrong, empty or missing key and for a store that has no key.
3. With the check enabled, a request to a store endpoint without a valid `Bearer` header returns HTTP 401 with `WWW-Authenticate: Bearer` and the `Missing store API key` body.
4. With the check enabled, a request with the store's own key succeeds on every store endpoint: catalog import, products, product stats, events import and events.
5. With the check enabled, one store's key used on another store returns HTTP 403 with the `Invalid store API key` body, and the other store's data is neither returned nor changed.
6. Creating a new key for a store makes the old key return HTTP 403 and the new key succeed.
7. A rejected import returns 401 or 403 even when its CSV is invalid, and stores nothing.
8. Without the check (plain `create_app`), requests need no key and a supplied header is ignored. The module-level `app` enables the check only when `MOTIVE_STORE_AUTH` is `required`.
9. `python -m scripts.create_store_key STORE_ID --db PATH` prints one key that `verify` accepts for that store.

## Tests
File: `tests/test_S3_04_store_keys.py`. Test names start with `test_S3_04_`. Each test uses a temporary SQLite file. API tests use `TestClient(require_store_keys(create_app(db), db))` with stores `a` and `b`, each holding one catalog product and one event imported through `EventStore`.

- `test_S3_04_key_format_and_storage`: creates two keys; asserts the prefix, the length, that they differ, and that the key text does not appear in any `store_keys` column or anywhere in the database file. Covers 1.
- `test_S3_04_verify`: asserts `verify` is `True` for the current key on a reopened `StoreKeys`, and `False` for a wrong key, `''`, `None`, another store's key and a store with no key; asserts a blank store ID raises `ImportValidationError`. Covers 2.
- `test_S3_04_missing_key_is_401`: calls each store endpoint with no header, with `Basic abc`, and with `Bearer` and no key; asserts 401, the `WWW-Authenticate` header and the exact body. Covers 3.
- `test_S3_04_own_key_allows_every_endpoint`: with store `a`'s key, imports a catalog and events and reads products, product stats and events; asserts 200 and the expected data; repeats one read with `bearer` in lower case. Covers 4.
- `test_S3_04_other_store_key_is_403`: uses store `a`'s key on every store `b` endpoint, including a URL-encoded store ID; asserts 403 and the exact body, that no store `b` data is in the response, and that store `b`'s products and events are unchanged. Covers 5.
- `test_S3_04_rotation_revokes_old_key`: creates a second key for store `a`; asserts the first key now gets 403 and the second gets 200. Covers 6.
- `test_S3_04_rejected_import_stores_nothing`: posts an invalid CSV and a valid CSV to both import endpoints with no key and with the wrong key; asserts 401 and 403 (never 400) and unchanged row counts. Covers 7.
- `test_S3_04_disabled_by_default`: with plain `create_app(db)`, asserts requests succeed with no header and with a wrong key; reloads `api.store` with `MOTIVE_STORE_AUTH` unset, `off` and `Required` and asserts only the last returns 401 without a key. Covers 8.
- `test_S3_04_cli_prints_working_key`: runs `python -m scripts.create_store_key a --db <tmp path>` in a subprocess; asserts exit code 0, a single output line, and that `verify('a', <output>)` is `True`. Covers 9.
