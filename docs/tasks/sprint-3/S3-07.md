# Add view-to-cart and view-to-purchase rates to product stats

## Description
Serves the Product-numbers story (store owners see how each product is performing). S2-07 returns raw view, cart and purchase counts for each product, and S2-08 lets the owner pick a date range. Raw counts make it hard to compare a product with 1,000 views against one with 20. This task adds two conversion rates to every item that `GET /stores/{store_id}/products/stats` returns, so the owner can see how often a view turns into a cart or a purchase. The rates use the same counts as the item, so they follow the date range from S2-08.

Out of scope: sorting by a rate (S3-08), showing rates on the dashboard (S3-10), store-wide totals or averages, rates per shopper or per session, and owner authentication.

## Specs
- Each item from `get_product_stats(db_path, store_id, limit=50, offset=0, start=None, end=None)` in `src/product_event_stats.py` gets two new fields:
  ```json
  {"product_id": "p1", "name": "Blue Mug", "category": "kitchen",
   "views": 3, "carts": 1, "purchases": 1,
   "view_to_cart_rate": 0.3333, "view_to_purchase_rate": 0.3333}
  ```
- New function `rate(count, views)` in `src/product_event_stats.py`:
  - `view_to_cart_rate = rate(carts, views)` and `view_to_purchase_rate = rate(purchases, views)`.
  - The result is `count / views` rounded to 4 decimal places.
  - When `views` is 0 the result is `None` (`null` in JSON), because there is nothing to divide by. This includes products with no events and products with carts or purchases but no views.
  - The rate is not capped at 1. Shoppers can add to cart without a recorded view, so a product with 1 view and 2 carts has a `view_to_cart_rate` of 2.0.
- The rates use the item's own `views`, `carts` and `purchases`, so with `start` and `end` they only count events inside the window.
- `GET /stores/{store_id}/products/stats` in `api/store.py` returns the new fields with no change to the endpoint itself. Paging, `total`, ordering and errors stay the same as S2-07 and S2-08.

## Requirements
- No change to the SQL query, the database schema or the import code. The rates are worked out in Python from the counts the query already returns.
- No new libraries.
- The S2-07 tests compare whole items, so their three expected items (`P1`, `P2`, `P3` in `tests/test_S2_07_product_stats.py`) gain the two rate fields. No other S2-07 or S2-08 test changes, and every existing test must keep passing.

## Acceptance criteria
1. Each item has `view_to_cart_rate` equal to carts / views and `view_to_purchase_rate` equal to purchases / views, rounded to 4 decimal places.
2. A product with 0 views has `null` for both rates, both when it has no events at all and when it has carts or purchases but no views.
3. A rate above 1 is returned as is, not capped.
4. With `start` and `end`, the rates are worked out from the counts inside the window.
5. `GET /stores/{store_id}/products/stats` returns HTTP 200 with both rate fields on every item, and `null` where views are 0.
6. The S2-07 and S2-08 tests pass, with only the S2-07 expected items updated to include the rates.

## Tests
File: `tests/test_S3_07_conversion_rates.py`
Setup for all: a temporary SQLite file (pytest `tmp_path`) filled with `EventStore` from S2-04. Store `store-a` imports products `p1` to `p5`. `p1` has views on 2026-10-01, 10-02 and 10-03, a cart on 10-02 and a purchase on 10-03. `p2` has 4 views, 2 carts and 1 purchase. `p3` has no events. `p4` has 1 cart and no views. `p5` has 1 view and 2 carts. API tests use `TestClient(create_app(<tmp database path>))`.

- `test_S3_07_rates_match_counts`: asserts `p1` has rates 0.3333 and 0.3333 (1 of 3, rounded), and `p2` has 0.5 and 0.25. Covers 1.
- `test_S3_07_no_views_gives_null`: asserts `p3` and `p4` both have `None` for both rates. Covers 2.
- `test_S3_07_rate_not_capped`: asserts `p5` has a `view_to_cart_rate` of 2.0 and a `view_to_purchase_rate` of 0.0. Covers 3.
- `test_S3_07_rates_follow_date_range`: asks for 2026-10-01T00:00:00Z to 2026-10-03T00:00:00Z and asserts `p1` has 2 views, 1 cart and 0 purchases, with rates 0.5 and 0.0. Covers 4.
- `test_S3_07_api_returns_rates`: calls `GET /stores/store-a/products/stats`, asserts status 200, that every item has both rate fields, and that `p3` has `null` for both. Covers 5.
- `tests/test_S2_07_product_stats.py` and `tests/test_S2_08_date_filter.py` run and pass with only `P1`, `P2` and `P3` updated. Covers 6.
